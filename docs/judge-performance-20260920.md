## 已实现

| 范围 | 实现 |
| --- | --- |
| Judge Service HTTP | 一个判题或公开运行生命周期内复用 `httpx.AsyncClient`；正常结束、异常和取消均关闭；保留 batch token 校验和顺序恢复。 |
| 超时与恢复 | 提交、查询及 sleep 受剩余预算约束；执行中使用单调时钟，重启根据已保存的墙钟截止时间恢复。旧版仅保存 tokens 的请求以原创建时间作为预算起点。 |
| 提交响应不确定 | POST 前保存 `dispatching` 标记，取得 tokens 后清除；重启看到未解决标记时返回系统错误，不自动再次派发学生程序。没有新增 POST 自动重试。 |
| SQLite | 启动恢复时初始化并缓存按数据库路径隔离的存储实例；状态接口只查询 id、submission_id、status、result；连接在事务结束后关闭。保留 tokens 和停止决定的落盘。 |
| 浏览器 | 进行中每轮只请求状态摘要；终态完整读取一次提交记录。网络失败指数退避，上限 15 秒；后台标签页至少 5 秒。切换提交和卸载会使旧响应失效；重新进入未完成提交时恢复轮询。 |
| LMS 补查 | 状态接口检查读权限后返回本地摘要，不等待 Judge Service。Redis 站点隔离锁、3 秒时间窗及 RQ job_id 去重合并补查。 |
| 丢失回调对账 | `scheduler_events.all` 分页扫描活动提交，向短队列派发补查，浏览器关闭后仍可推进。每轮最多 100 条，游标轮转避免异常旧提交长期挡住后续提交。 |
| 更新竞态 | 补查和回调在行锁内重新读取当前记录，检查请求身份与版本；终态不被旧进度覆盖。派发响应也不会覆盖先到达的完成回调。 |
| 版本数据 | 同一次结果处理复用已解析的版本测试集，避免失败反馈再次读取和解析版本。未引入跨请求模板缓存。 |
| Judge0 缓存 | 两条部署路径同步使用跨进程互斥的限频扫描，最短 300 秒一次。保留 24 小时 TTL、目录锁、过期复查、原子发布和每点独立二进制副本。 |

## 观测开关

- LMS：站点配置 `judge_timing_enabled: true`，记录版本读取、JSON 解析、请求构建及派发 HTTP 耗时到 `judge_performance` 日志。HTTP 事件包含 requests 的请求序列化成本，不将其误报成纯网络耗时。
- Judge Service：进程环境 `JUDGE_TIMING_ENABLED=1`，输出 `judge_timing` 事件：提交/查询 HTTP、sleep、比较、状态序列化、状态字节数、SQLite 写入提交、结果保存、回调、事件循环延迟和活跃任务数。tokens 与 compile_group 关联 request_id。
- Judge0：`CODEPLUS_JUDGE_TIMING=1`，输出出队、沙箱初始化、缓存锁等待/命中/清理、真实编译、run、verify、cleanup、最终 save 及成功保存事件。Compose 已暴露此变量，默认关闭。

新日志只记录身份和耗时元数据，不记录学生源码、测试输入或答案。`finished_at` 的原语义未改变。正常成功路径的 `result_persisted` 是最终 save 返回成功后的事件；异常和非缓存编译错误路径不能用该事件的缺失推断任务尚未结束。跨机器比较需另外确认时钟偏差；活跃任务数也不等同于 Judge0 队列长度。
